# SiteForge Preview Builder

Choose the workflow from the private input files before making changes.

- When `../input/revision-scope.json` exists, this is a narrowly scoped refinement of restored private source. Read that file first. Do not read `manifest.json` or `source-pages/`; they are deliberately absent for this lower-context workflow. Change only the `allowedSourcePaths` listed in the revision scope, preserve the selected page's provenance marker and factual content, and do not add or strengthen business claims. The restored page is the approved baseline, not permission to recreate unrelated pages.
- Otherwise, build a complete, high-quality static business website in `src/` from `../input/manifest.json`. The manifest is the source of truth. Do not edit it or invent claims, reviews, credentials, prices, guarantees, locations, contact details, services, or testimonials.
- For a normal build, `../input/source-pages/index.json` lists every selected source page. Build every listed `outputPath`; for each one, read its linked content file and add a `siteforge-source-url` meta tag containing that entry's exact `sourceUrl`.
- In a normal build, treat captured paragraphs, headings, lists, forms, navigation, tools, legal content, and calls to action as content to improve, not disposable filler. Rewrite and shorten it when that makes the page clearer, but retain necessary information and do not strengthen or add claims.
- In a normal build, `approvedCapabilities` in the manifest is the only approved dynamic scope. For managed content, authentication, payments, external integrations, or server-side workflows, make an honest front-end preview of the approved visitor flow and add `src/BUILD_NOTES.md` describing the required production service, data, and approval boundary. Never invent credentials, live submissions, transactions, account data, or a working backend. A scoped refinement must not add dynamic scope or `BUILD_NOTES.md`.
- Assets in `src/assets/` are the only approved visual assets that may be reused. Do not fetch remote images, fonts, scripts, stylesheets, or libraries.
- Create all required pages as static HTML files in `src/` and use relative links and paths only. The private preview host serves this directory beneath a protected path.
- Build mobile-first, then provide intentional tablet and desktop layouts. Do not merely shrink a desktop layout.
- Read `feature-contracts/mobile-navigation.md` before implementing any page. It is the required mobile-navigation feature contract. Implement it in the generated page's own local HTML, CSS, and JavaScript: this is deliberately a creative, page-specific feature, not a locked runtime treatment.
- Use semantic landmarks, one logical H1 per page, labelled forms, visible focus styles, accessible contrast, keyboard-friendly navigation, and reduced-motion behaviour.
- Keep the locked `src/main.js` file and reference it with a local deferred `<script src="main.js" defer></script>` on every generated page. It provides SiteForge's built-in progressive viewport motion for headings and containers. Motion is a default implementation detail, not something the workspace member has to request: use the reveal structure deliberately, make the first hero heading, supporting copy, and visual media distinct elements so their entrance can be seen after the logo introduction, and when captured content presents a factual number as a metric, use `data-counter` when it improves scanning. Never invent a metric, add a motion dependency, a remote script, or motion that hides essential content.
- Build the complete visual system in `src/styles.css` by default: it must style the header, hero, page sections, controls, responsive layouts, and generated mobile navigation. Do not link `homepage.css`, `app.css`, or another extra stylesheet unless you create that exact file in `src/`; a linked but absent stylesheet makes the private preview render like raw HTML. Before finishing, inspect every local `<link rel="stylesheet">` and `<script src>` in the generated HTML and confirm its file exists under `src/`.
- When the normal-build manifest or scoped revision file supplies an approved primary logo, preserve or use that exact asset in the header and footer. Mark the actual header logo image or its immediate wrapper with `data-siteforge-brand-logo`; the built-in runtime fades that same mark into the centre, lets it rise and scale gently with a brief preparation message, then carries it into the navigation on a first visit. Choose the treatment autonomously to suit the brand. Use `data-siteforge-intro="quiet"` on `<html>` only when a deliberately quieter reveal suits the site. Do not create a second loader, a fake percentage, a generic wordmark, or a transition that delays content, controls, or reduced-motion users.
- Use a distinctive, restrained design appropriate to the business. Avoid generic AI visual clutter, fake badges, decorative gradients, unsupported trust claims, and stock-like placeholders.
- Keep source HTML, CSS, and JavaScript maintainable. Use custom properties as design tokens and reusable component classes where repetition exists.
- Do not edit `package.json`, `scripts/`, or files outside `src/`. Run `npm run build` before finishing.
